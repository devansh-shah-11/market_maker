\prompt{Describe one possible execution of the hotpath.}
Lets take the scenario from \texttt{basic} at 1,205,000\,ns. Our quotes are bid 100.01 and ask 100.04. A competitor's new 100.01 bid (100 shares) arrives in the feed, and its entry time is stamped. \texttt{OnMarketData} decodes the header with \texttt{memcpy} and checks the sequence number. It then decodes the \texttt{AddOrder}, and \texttt{Apply} writes it into the flat array at its ref and adds 100 shares to the 100.01 slot of the bid ladder. That slot is above the old best of 100.00, so the cached top of book becomes 100.01 $\times$ 100. Our own 100.01 bid is already excluded from the believed book, so this thin bid is the only visiblse one. \texttt{Requote} passes the risk checks and copies the top. The microprice falls from 100.0285 to 100.02, since the thin bid sits next to a 300-share ask at 100.05. With the \$0.01 credit, which is recomputed even though nothing changed it, the desired prices are 100.01 and 100.03. \texttt{QuoteSide(Buy)} finds 100.01 equals the resting bid and returns, so nothing is sent. \texttt{QuoteSide(Sell)} finds 100.03 differs from the resting 100.04, so \texttt{SendQuote} appends to the history, \texttt{fprintf}s the decision log, and encodes and sends a \texttt{REPLACE}, and its departure time is stamped. \texttt{latency\_.Record} runs and the handler returns.

\prompt{Describe a flaw in the evaluation and a potential fix.}
The report averages (handler finish $-$ arrival) over every message, using \texttt{LatencyLog} for the finish time. That is not tick-to-trade: most messages send nothing, the clock stops when the handler returns rather than when the order leaves, and a mean hides the tail. Over 30 runs per fixture (\texttt{tools/latency\_compare.py}, orders pooled), only 1 of 48 messages in \texttt{quiet} sends; the report prints about 3,100\,ns but the median order takes about 15,200\,ns. In \texttt{basic} the report's mean is about 3,000\,ns, while the median order takes 666\,ns and the p99 is 22,900\,ns.

The capture tap already records each order's send time and the delivery that caused it, so \texttt{LatencyLog} is redundant. Instead, report send time minus that delivery's entry time for every order, as a distribution (median, p99, max) that keeps the cold first order; messages that send nothing then drop out. The log's report runs after the run, so we expect removing it to save little, but we did not measure this.

\prompt{Describe a flaw in the market maker and a potential fix.}
The risk checks (\texttt{RiskGate}) signal failure by throwing. The design justifies this by saying exceptions cost nothing when not thrown, and that once one is thrown ``we are no longer on the hotpath''. The first half is true; the second is not. None of the throws stops the market maker. \texttt{BookInvalid} makes \texttt{Requote} return and the resting quotes stay, so the next message is back on the hotpath at once. \texttt{PositionLimit} is caught in \texttt{QuoteSide}, which blocks only that side, so the other side's order is sent right after an exception was thrown and caught. While the position sits at the limit (as in \texttt{position}), this happens on every message. After a halt is latched, \texttt{CheckStanding} also throws on every later message. A throw allocates the exception object and a \texttt{std::runtime\_error} string, and then unwinds through tables, which typically costs microseconds (we did not isolate this). In \texttt{quiet}, \texttt{position} and \texttt{gap}, the first messages, which have an invalid book, took about 2--5\,$\mu$s each against 0--42\,ns for steady-state messages, but the cold start is mixed in with this, so it is only suggestive.

The fix is to have the checks return a status (a \texttt{[[nodiscard]]} enum or \texttt{bool}) and branch on it, which is a predictable compare costing about a nanosecond. The throw's one real benefit, that a check cannot be ignored, is kept by \texttt{[[nodiscard]]} with \texttt{-Werror=unused-result}. Orders do not change, so \texttt{make verify} should still pass. The cost is that safety is now enforced by the compiler flag and by discipline instead of by control flow, so a caller could still discard the result.
